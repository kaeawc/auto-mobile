# Android form factors: Android TV

Part of [Android form factors](form-factors.md).


TV navigation is a focus problem: D-pad keys can be sent and the focused element comes back in every observation. `focusNavigate` is the loop that connects them. `launchApp` tries `MAIN/LEANBACK_LAUNCHER` when `LAUNCHER` resolution finds no activity, including activity-query and package-dump fallbacks. `listApps` includes Leanback entry points in launchability on devices with `formFactor: "tv"`.

1. **Activate focused item.** `enter` activates the focused item on the verified image; `KEYCODE_DPAD_CENTER` is not needed and no `select` key exists. If a future TV image shows that `enter` does not activate, add `select` (`KEYCODE_DPAD_CENTER`) to **both** `SUPPORTED_INPUT_KEYS` and `INPUT_KEY_CODE_MAP`: `InputKeyName` derives from the first and the second is checked against it, so one entry alone does not compile.
2. **`focusNavigate({ until, direction?, maxSteps?, settleMs?, select? })`** (`src/features/action/FocusNavigate.ts`; tvOS reuses the loop through `src/features/tvos/TvosFocusNavigate.ts`, mapping arrows to Siri Remote directions and `enter` to `select`). Observe; stop if the focused element itself or a label it owns matches `until`; else press one D-pad key and repeat. A descendant cannot supply a match when the focused element is scrollable or a separately focusable/clickable control inside it contains that descendant; a card can still match its static child title. `until` matches on `text`, `contentDesc` and `resourceId`; `label` or `elementId`, given alone, names the target as `tapOn` does and pins it with `DpadTargetResolver` (`pinnedFocusOptions`), so a focused parent row cannot stand in for an independently actionable child (combined with other fields it is matched by the loop, which checks every field). Returns the path of focused elements. With `select`, a `focused` result also presses `enter` and reports `selected: true`, and a refused key throws; the tool always reports `selected` (required in its output schema, so a spilled response keeps it inline). The tool records navigation like `tapOn` (`recordsNavigation`), so a public select that changes screen becomes a replayable edge. The select press is reported as the call's dispatch (`ToolDispatchContext`), so the navigation graph times a recorded `focusNavigate` from the key that navigates, not from the first arrow.
   - Direction: given `direction`, else the arrow from the focused element's bounds centre toward the nearest `until` match; with no match on screen, `arrow_right` once per focused Leanback row header (a `row_header` inside the `browse_headers` grid) to enter its content pane, otherwise `arrow_down`. A scrollable headers grid can hide the target header below, so there the headers are scanned down first and `arrow_right` is pressed once `arrow_down` is refused at the last header.
   - Fallback: with a match on screen, a direction is never pressed twice from the same element in one call, and once the directions toward the target are spent the others are tried (perpendicular to the dominant axis, then away from the target), so focus can leave a container that traps it (#17209). Three consecutive presses in one direction that move focus without closing distance to the nearest match (a list scrolling under a fixed slot, a slider changing value) put that direction after the sideways escapes until focus moves another way or gets closer; backing away from the target comes after it, and once every escape from an element fails the direction is pressed again and not demoted for the rest of the call (a list with no side exit still scrolls to the footer). With no match on screen a Leanback row header first tries `arrow_right` once to reveal its content pane; if focus does not move, the scan continues down the headers. When no read has held the target yet, a horizontal row of cards whose labels have as many words and differ only in the last (`Trending card 1` … `5` for `Trending card 8`, `src/features/action/FocusRowSearch.ts`) is taken as the lazily composed row that holds it (#18027): the walk plans toward that row, then sweeps right until a press does not move focus and then left, never leaving the row; a sweep rather than per-element memory, because a scrolling row moves every card's bounds. If both ends refuse, the stuck message says the target was in no read and names the row and the focused element. A vertical list, a grid or a single matching card has no such row. Otherwise the absent target scans down, and its stuck or `maxSteps` message also says the target was in no read.
   - Stops on match, `maxSteps` (default 30), or when no untried direction is left on the current element (an explicit `direction` stops after two unchanged presses). A focused container holding the target is re-read after the settle delay up to twice per press; if it persists, the last direction continues within `maxSteps`. Those container reads do not update stuck/stall tracking or borrow a card label for the path. Focus counts as unchanged only when the focused element's identity fields, bounds and its descendant label all repeat, because a recycler row can keep fixed bounds while the list scrolls under it. The exception is a control that changes its own label in place (#17739): when a press changes the focused element's label but leaves its resource-id, class and bounds unchanged and the screen around it stays put (the same nodes at the same bounds, and no label that was already on screen shown somewhere else) and shows the new value (some node outside focus with a different resource-id shows a new label in place while another keeps its label), the press counts as unchanged and the control is keyed without its label for the rest of the call (a slider announcing its value, which would otherwise read as fresh focus on every value and run to `maxSteps`). With no such readout on screen, a press and its opposite that change the label and the control's `range-info` (a slider's current value) and then bring both back count as an in-place change too (#17209); a label round trip alone does not, because a one-slot recycler scrolled to another item and back reads the same way (#18255). Value readouts beside the control (a `Slider Value: 51%` text, a progress bar's description) show new values in place, so they do not count as the screen moving; a fixed-slot recycler row's neighbours shift by one slot, share its resource-id when they repage in place, or are absent when only one row is visible, so it still reads as moving. When such a control has no untried direction left, tab is pressed once and the walk retries; a `stuck` result after that names the control and the directions it consumed. That label is the first contained text or content-desc, falling back to a resource-id only when none has one, since a resource-id such as a Leanback card's `main_image` is shared by every card in a row. Statuses: `focused`, `max_steps`, `stuck`.
   - **Explore** (`src/features/navigation/focusDrivenInput.ts`). It resolves an input mode once per call: D-pad when the device's form factor or `ro.build.characteristics` says `tv`, touch otherwise (an unreadable trait falls back to touch). In D-pad mode `explore` replaces each tap with `focusNavigate { until, select: true }`, where `until` is the element's tap selector as `elementId` or `label`, pinned to the element `tapOn` would tap (so a focused row cannot stand in for a chosen child control) (an element whose selector needs an occurrence `index` is skipped, since `until` cannot tell duplicates apart); it records that call, so `navigateTo` replays the edge as the same D-pad walk. It does not swipe or select a newly found scrollable container, since moving focus is what scrolls it; it advances it instead (`src/features/action/FocusListAdvance.ts`, unrecorded): when focus is elsewhere (discovery picks the list, not what holds focus) it first steers focus toward the container, then presses down a list whose visible rows are stacked (right along a rail whose rows sit side by side, judged from the row-level nodes only, not the labels inside them; the container's long axis without two rows) until a named row that was not on the first read appears inside the container, and treats the list as exhausted when focus does not move for two presses, leaves the list after entering it, or 12 presses pass along it (steering in has its own 12-press bound) (rows already seen never count, so a wrapping list ends on the bound). The advance itself is not recorded. The walk to a card an advance revealed in a horizontal rail is recorded with the rail's `direction: "right"` (`src/features/navigation/RevealedListRows.ts`, which keeps each advanced list's revealed row identities for the exploration), because on replay the rail is back at its first cards and the default absent-target scan within the rail presses down. A card counts as revealed when its own identity or any one of its names was among the advance's new rows, since explore labels an unlabelled card from its child while the advance reports the two separately. The direction is added only while focus is in that rail on the card's row at or before it, so the live walk also reaches it (a control below the cards keeps the default walk); a row revealed in a vertical list keeps the default walk, whose downward scan already scrolls the list. A recorded `focusNavigate` that targets a scrollable container still replays; validate mode skips a recorded edge it cannot act on this way (a `swipeOn`, or an element with no focus target) rather than retrying it. Like a tap, the walk flushes pending post-action captures first, and a successful select waits a bounded settle (1 s) while its record is live, so the navigation it causes is attributed to it. Validate mode replays a recorded `focusNavigate` edge as a focus walk on any device, touch included, with its recorded `until`, walk options and `select` (a call that navigated on focus alone presses no enter), and finds the on-screen element the way the replay will: a lone `label` or `elementId` with the same resolver the walk pins it with (a resolved static child maps to the smallest candidate containing it, as focus on that owner counts), any other target with `focusNavigate`'s matcher (every `until` field on one element, exact labels first; a match only on a static descendant in the hierarchy maps to the candidate containing it), falling back to the label fields alone when the target is a label inside a clickable row. The abort signal reaches each key press, so a cancelled run sends no further keys, and it ends the waits between them: the input-mode probe, each walk's or advance's per-press settle, and the select settle, so a cancel waits at most for the key press or hierarchy read in flight. A recorded `tapOn` edge replays as `tapOn`, which takes the D-pad path itself on a device without a touchscreen.

`focusedElement` follows Leanback's focus ring (`focused: true`). `swipeOn` works on the `android-tv` image, which reports a touchscreen though `getevent -pl` lists no touch input device (only `gpio-keys`). A device counts as touchless when `pm has-feature android.hardware.touchscreen` is `false`, or when it is `true` but `android.software.leanback` or `android.hardware.type.television` is `true` (TV emulator images declare the touchscreen anyway); an unreadable TV-feature probe keeps touch and is not cached. On a touchless device `tapOn` with a `text` or `elementId` selector and a plain tap runs `focusNavigate` to the match and presses `enter`, returning `inputMethod: "dpad"` and the focus walk (`src/features/action/DpadTapOn.ts`); On each focus read the target is resolved with the touch path's own `ElementSelector` and options (`src/features/action/DpadTargetResolver.ts`), so placeholder (hint-text) fallback, exact-before-contains, ranking, actionable-ancestor promotion and synthetic `view-id`s pick the same element for D-pad and touch; focus then steers to that element's bounds, and a resolved target that is itself clickable or focusable must hold focus: a focused parent row does not count for an independently actionable child inside it. Only when a read carries no hierarchy does `FocusNavigate` match itself: `text` against text or content-desc after the resolver's normalization, exact matches first, the first-ranked match (smallest area, then hierarchy order) pinned, and `elementId` against the native `resource-id` or synthetic `view-id`. Enter is not pressed when the request was cancelled during navigation. `pm has-feature` prints `false` and exits 1 for a missing feature, so that rejected output is read as the answer. The probe answer is cached per device incarnation for five minutes and dropped when the serial's device is replaced or killed, so another AVD booted on the same serial is probed again; a failed probe keeps the touch path. On a touchless device a request only a touch tap can serve (sibling, container, index, searchUntil, ensureChecked with either value, layer, display, exactText, a non-`first` selection strategy, a `testTag` or `textAny` selector, another action) is refused with an `ActionableError` naming each such part and the plain-selector D-pad form, because an injected touch tap there is a silent no-op that would report success; the probe therefore runs before that check, and a device with a touchscreen still takes the touch path. Semantic-link requests (`selector.accessibilityLink`, owner-scoped `subtext`) skip both the probe and the refusal: the accessibility service invokes the span's click handler, so no touch is injected. This mirrors tvOS, where `tapOn` already selects by focus. The leanback rule has been verified on both emulator images; real touchless hardware remains unverified. `focusNavigate` accepts a static child label owned by the focused control, but continues navigating when a focused container merely holds a separately actionable target. Prototype overlay buttons are not reachable with D-pad focus.
