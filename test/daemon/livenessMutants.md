## Start-wiring mutants (#11441 sweep)

One wire of `Daemon.start()` or `UnixSocketServer.start()` is cut per mutant. Rows are in the
matrix's "start wiring a daemon only has once started" block unless a file or block is named.

| Mutant (cut wire)                                                                                | Behaviour lost                                                              | Scenario row that kills it                                                                                                                                                                                                                                                  |
| ------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `daemon.ts`: `setSessionExecutionDeadlineLookup`                                                 | a call past its own request deadline still vetoes a release, to the ceiling | matrix, "daemon release wiring": "a call that never settles holds the session until its caller is answered with a timeout, aborting nothing; the grace after that deadline frees the device and aborts the call"                                                            |
| `daemon.ts`: `reownRehydratedManagedExecutions` after startup rehydration, or its body           | a rehydrated managed execution's slot still names the dead daemon           | "a broker binding names the daemon that holds its execution: the restarted daemon records itself as the owner"                                                                                                                                                              |
| `daemon.ts`: `setLateRehydrationListener`                                                        | the same, for a session that rehydrates after the startup deadline          | "a managed execution whose session finishes rehydrating after the startup deadline is re-owned when it does"                                                                                                                                                                |
| `socketServer.ts`: `clearBoundMcpClientsForReleasedSession` on a release                         | a released session's loopback transport stays open while its proxy connects | "a released session's MCP transport is closed five minutes after the release although its proxy stays connected; a held session's stays open"                                                                                                                               |
| `socketServer.ts`: `liftStrokesHeldBy` on a release                                              | a pointer left down stays down on the next owner's device                   | "a stroke its holder left down is lifted when the holder's session is released; a stroke the holder ended is not lifted again"                                                                                                                                              |
| `socketServer.ts`: the `ResourceUpdatedBroadcaster` subscription                                 | a subscribed proxy is never told its resource changed                       | "the agent's resource subscription is pushed each change to that resource, across a daemon restart, and nothing once it unsubscribes"                                                                                                                                       |
| `socketServer.ts`: `lifecycleGeneration += 1` in `beginAccepting`                                | none: EQUIVALENT                                                            | no row. A server is started once, and `close()` bumps the generation itself, so a client creation can only be superseded by a close; a daemon builds a new server for every start, so nothing it can do tells the two apart.                                                |
| `daemon.ts`: `startHost.startServicesAfterSocketBind()` / `startHost.startMaintenanceMonitors()` | the aux sockets, PID identity and monitors of a started daemon              | `livenessScenarioHarness.test.ts`: "each daemon process asks its host for every step once, the services and monitors after the socket bind". A CALL-ORDER row: both steps touch the machine and are no-ops in the harness, so only that the start asks for them is visible. |
| `devicePool.ts`: the peer-claim pre-check moved to just before `assignDeviceToBoundSession`      | an acquisition refused for a peer's claim first discovers the peer's device | "an acquisition of a device a peer daemon claims is refused before this daemon looks at the device; once the peer lets go it is acquired"                                                                                                                                   |

The request-deadline row needed the harness's stand-in for the daemon's tool-call entry
(`RealToolCallPath.call`) to record the deadline the socket server stamps on a forwarded call, as
`src/server/index.ts` does. Before that no harness execution carried a deadline, so every veto ran
to the 30 min ceiling and the old #10820 row pinned a six-minute hold production does not have.
The ceiling row now drives a call that reaches the entry with no deadline.

## Seeded harness invariants (pool level)

`poolOwnershipConcurrency.slotsAndTools.property.test.ts` runs the `slots`, `tools` and
`slotsAndTools` profiles with `bindings: true`; after every step the harness checks, on top of
the ownership invariants:

- `non-owner-control-ran`: no non-owner control (`tapOn`, `ide/*` mutation, write SQL) ever runs a
  handler. A slot device is judged once its slot is older than the one-second admission snapshot.
- `slot-device-allocated-generically`: no generic session is created on a device a slot holds.
- `tool-read-stamped-activity`: a read, with or without a session, never moves an idle clock.
- `slot-execution-refused`: a slot's own execution is never refused its device.
